## Обзор

Серверная схема описана в `app/supabase/migrations/20261019120000_data_model.sql`. Клиент повторяет её через одну карту колонок - `app/services/powersync/columns.ts`. Правила ниже объясняют, почему таблицы устроены именно так; каждая новая таблица и колонка им следует.

## Хранение

1. **Сущность** (своя жизнь, много на пользователя, на неё ссылаются): своя таблица (`wallets`, `categories`, `transactions`).
2. **Одна запись на (пользователь, вещь)**: своя таблица с **детерминированным id**, чтобы одновременное создание на двух офлайн-устройствах попало в одну строку. Id - это части ключа через `:`, без префикса таблицы:
   - одна часть - сам id: `loans.id` и `bank_reports.id` равны id кошелька;
   - несколько частей склеиваются: `loan_schedule_overrides.id` = `<loanId>:<paymentNumber>`;
   - если часть может совпасть у двух пользователей (встроенная категория, тип транзакции, код валюты), id пользователя тоже входит в ключ: `<userId>:<kind>:<targetId>`. Формат закреплён check-ограничением, так что чужой id занять нельзя.
3. **Детали одного вида сущности** (займ, цифры банка): таблица 1:1, где `id` равен id сущности, без отдельной колонки `wallet_id`. Одиночное поле остаётся nullable-колонкой общей таблицы (`wallets.credit_limit`), пока не появится второе. Серверный запрос, который джойнит таблицу 1:1 по id, сверяет и `user_id`: id пишет клиент, внешнего ключа нет.
4. **Скалярная настройка пользователя**: типизированная колонка в `user_settings`. Фича со своей группой настроек получает таблицу 1:1 с `id = user_id` (`forecast_settings`).
5. **Состояние UI только для устройства**: `useStorage`, никогда не сервер. Оно не мигрирует: когда меняются id внутри, оно начинается заново со значений по умолчанию.
6. **JSON-колонка** только для непрозрачного конфига, который один экран читает и пишет целиком (`stat_views.config`, `stat_views.auto_rule`, `exchange_rates.rates`). Нужны ключ `version`, значения по умолчанию в zod, проверка `jsonb_typeof = 'object'` и вид `json` в карте колонок. Для разрешения конфликтов JSON - одна колонка: две офлайн-правки разных ключей перезаписывают друг друга.

## Каждая синхронизируемая таблица

- **`id`**: генерируется на клиенте как UUIDv7 функцией `generateId` (`app/utils/generateId.ts`), упорядочен по времени, поэтому вставки в индекс локальны. Ссылка на него тоже `uuid`. Детерминированный составной id (`<loanId>:<paymentNumber>`) и колонка, которая может хранить зарезервированный id (`category_id`, `display_overrides.target_id`), - `text`; детерминированный id, равный другому id (`loans.id`, `bank_reports.id`), - `uuid`. На клиенте любой id - непрозрачная строка.
- **Владелец и время**: `user_id uuid not null`, `created_at` и `updated_at` (`bigint` мс, `not null`, с серверным значением по умолчанию для SQL и записи под service role). `updated_at` выставляет каждый пишущий.
- **Доступ**: RLS владельца через одну функцию `private.can_access(user_id)`. Она `language sql stable` и не security definer, поэтому планировщик встраивает её как `user_id = (select auth.uid())` без затрат на строку. Её вызывает каждая политика каждой таблицы, так что совместный доступ позже меняет одну функцию. У каждой таблицы включён RLS, нет прав у `anon`, есть `select, insert, update, delete` у `authenticated`.
- **Индексы**: серверный индекс для RLS и запросов edge-функций, обычно по `user_id`; составной индекс, начинающийся с `user_id`, заменяет простой (`transactions (user_id, date)`, `loan_schedule_overrides (user_id, loan_id)`). В клиентской SQLite индексов нет: хранилища читают таблицы целиком.
- **Синхронизация**: таблица входит в публикацию `powersync` **и** имеет строку в `app/powersync/config/sync-config.yaml`. Одна строка в правилах синхронизации ничего не синхронизирует.
- `exchange_rates` - единственная глобальная таблица: без `user_id`, клиенты только читают, пишет edge-функция `fetch-rates`.

## Конфликты

Загрузка правки - это PATCH только с изменёнными колонками, и сервер применяет его как есть: **последняя загрузка побеждает по каждой колонке**. Защиты от устаревшей записи нет: при одном владельце и паре устройств потеря редка (офлайн-правка той же колонки приходит после более новой), а защита на уровне строки молча теряла бы и офлайн-правки других колонок.

Удаления жёсткие. Детерминированный id, созданный заново офлайн, воскрешает строку, удалённую на другом устройстве; это принято.

## Без внешних ключей

У синхронизируемых таблиц нет внешних ключей. Одно устройство удаляет кошелёк, другое офлайн добавляет в него транзакцию; при загрузке ограничение отклонило бы транзакцию, фатальная ошибка выкинула бы её из очереди, и она потерялась бы. Вместо этого:

- читатели пропускают строки, чья цель исчезла, а удаление убирает зависимые (удаление кошелька удаляет его транзакции, займ и строку `bank_reports`);
- check-ограничения внутри строки остаются;
- у синхронизируемой таблицы нет уникальных ограничений между строками (они так же отклонили бы офлайн-создание); уникальность дают детерминированные id;
- серверные таблицы могут использовать внешние ключи и уникальные ограничения.

Check-ограничение, которое клиент не проверяет так же, теряет строку при загрузке, поэтому у каждого ограничения есть такая же клиентская проверка (zod-схемы, например `trnItemSchema` в `app/app/components/trns/types.ts`) с тестом на те же случаи. Правила между строками (перевод в одной валюте с двумя разными суммами, смена валюты кошелька, у которого есть строки) - только клиентские.

## Значения-перечисления

Колонки-перечисления - `text` с check-ограничением (из enum в Postgres нельзя удалить значение). Значения в snake_case: `credit_card`, `reduce_payment`, `full_debt`. Диапазоны и знаки тоже проверяются.

## Деньги

- Деньги - `bigint` в **минорных единицах** валюты (копейки, центы, сатоши): точно в Postgres, SQLite и JS (безопасно до 2^53). Денежная колонка называется `amount` или оканчивается на `_amount`; `credit_limit` тоже деньги.
- Масштаб каждой валюты закреплён навсегда в `app/utils/money/scale.ts`: минорная единица ISO 4217 для фиата; крипта - родные знаки, но не больше 9 (`BTC` 8, `USDT` 6, `ETH` и `SOL` 9). Он никогда не читается из `Intl` во время работы: сохранённая сумма не должна менять смысл, когда меняются валютные данные браузера. Валюта, которой нет в таблице (и среди пользовательских валют), отклоняется. Пользовательская валюта хранит свой `scale` в `currencies`.
- `toMinor`, `fromMinor` и `formatMinor` лежат в том же модуле; edge-функции и внешние писатели используют те же масштабы. Отображение делит на масштаб, ввод разбирается в минорные единицы.
- Конвертация между валютами идёт без округления через всю сумму и **округляется один раз, в конце** (`getTotal` возвращает минорные единицы базовой валюты, каждую округлённую один раз).
- Валюта суммы - `currency_code` строки, а если его нет, валюта кошелька, которому строка принадлежит (`transactions`, `bank_reports`, `loans`, `loan_schedule_overrides`). Смена валюты кошелька с суммами изменила бы их смысл, поэтому это клиентское правило. Сумма в базовой валюте хранит свой `currency_code` (`forecast_categories.monthly_amount`).
- Курсы и проценты - `double precision`, имя называет единицу (`annual_rate_percent`).

## Дни и моменты

- **Календарный день**: `bigint` мс полуночи UTC, имя оканчивается на `_date` (просто `date` можно для собственного дня строки), с check-ограничением `% 86400000 = 0`. Момент времени, записанный в колонку дня, отклоняется, а не попадает на день, зависящий от часового пояса читателя.
- **Момент**: `bigint` мс, имя оканчивается на `_at`.

## Булевы и коды

Булевы называются `is_` / `has_`: `boolean` в Postgres, 0/1 в SQLite. Nullable-булево означает «наследовать», и комментарий колонки называет источник (`wallets.is_in_forecast`: null следует `is_withdrawable`). Валюты - `currency_code` (ISO 4217 или свой код).

## Именование

- Таблицы и колонки в snake_case, TypeScript в camelCase. Соответствие механическое (`from_wallet_id` <-> `fromWalletId`), его делает карта колонок.
- Таблицы - существительные во множественном числе без сокращений; таблицы фичи имеют общий префикс (`loans`, `loan_schedule_overrides`).
- Ссылки - `<entity>_id`. Никаких зарезервированных слов SQL (`order`, `desc`, `user`); незарезервированные вроде `date`, `type`, `name` допустимы.
- Имя говорит, что это за значение, а не откуда оно. Если источник важен, это таблица (`bank_reports`), а не префикс колонки.
- Имена колонок живут и в строках, которые typecheck не видит: сырой SQL в `app/services/powersync/mutations.ts` и запросы `watchTable` в хранилищах, правила синхронизации, фильтры PostgREST в edge-функциях. Переименование ищет по всем.

## Карта колонок

`TABLE_COLUMNS` в `app/services/powersync/columns.ts` перечисляет каждую синхронизируемую колонку с её видом: `bool`, `day`, `instant`, `int`, `json`, `money`, `real`, `text`, `uuid`. Из неё клиент строит:

- `AppSchema` (`AppSchema.ts`): таблицы SQLite; `real` - real, `text`, `uuid` и `json` - text, всё остальное - integer;
- `rowToItem` / `itemToRow`: snake_case <-> camelCase, 0/1 <-> boolean, JSON-текст <-> объект, числа при записи округляются до целых; null-колонки при чтении пропускаются, чтобы сработали значения по умолчанию zod;
- `JSON_COLUMNS`: колонки, которые коннектор загрузки отправляет как JSON-объекты. Без этого JSON-колонка ушла бы строкой, не прошла бы проверку `jsonb_typeof`, и операция была бы выброшена как фатальная.

Проверка на этапе компиляции в конце файла держит карту равной сгенерированным типам Postgres: колонка, добавленная в базу, но не в карту, роняет typecheck.

## Процесс

- **Одна миграция на фичу.** Вместе с ней - правило синхронизации, запись в карте колонок, преобразования с тестами, путь демо-режима и edge-функции, если они касаются таблицы.
- **Сгенерированные типы**: `pnpm db:types` (в `app/`) пишет `app/services/supabase/database.types.ts` из локальной базы. Файл лежит в репозитории; его используют проверка карты колонок и edge-функции.
- **Сброс по версии схемы**: изменение схемы данных повышает `DATA_SCHEMA` в `app/services/powersync/db.ts`. При загрузке `ensureDataSchema()` (`app/app/composables/useDataSchema.ts`) сравнивает её со значением на устройстве; если они различаются, удаляются локальная SQLite (она заново синхронизируется с сервера), кэш хранилищ холодного старта и демо-данные (демо-пользователь начинает с экрана входа). Операции загрузки, ещё стоящие в очереди под старой схемой, теряются.
- **Внешние писатели**: приложение полностью работает без внешних писателей. Каждое значение, которое они могут дать (`bank_reports`, `loan_schedule_overrides` с `source = 'bank'`), необязательно и вводится вручную, а каждая фича, которая его читает, откатывается к собственному расчёту приложения. Внешний писатель через API подчиняется тем же правилам: RLS или service role, ограничения, `updated_at`.

## Схема

У всех синхронизируемых таблиц также есть `id`, `user_id`, `created_at`, `updated_at`, если не сказано иное.

### `transactions`

`type` (`expense`, `income`, `transfer`, `adjustment`), `date` (календарный день), `from_wallet_id` / `from_amount`, `to_wallet_id` / `to_amount`, `category_id`, `description`. `created_at` - момент ввода строки, сохраняется при правках. Модель потоков описана в [Типах транзакций](/ru/reference/transaction-types).

### `wallets`

`name`, `color`, `currency_code`, `type` (`cash`, `bank_account`, `credit_card`, `loan`, `deposit`, `crypto`, `debt`), `sort_order` (один порядок кошельков на всех устройствах), `description`, `is_archived`, `is_excluded_from_total`, `is_withdrawable`, `is_in_forecast` (nullable: null следует `is_withdrawable`), `credit_limit` (деньги, null, если не `credit_card`).

### `bank_reports`

`id` = id кошелька, любого типа. Последние цифры, которые показывает банк по кошельку, введённые вручную или записанные через API; каждая колонка nullable:

| Колонка | Смысл |
|---------|-------|
| `balance_amount`, `balance_date` | Баланс, который показывает банк, и день, к которому он относится (задаются вместе) |
| `statement_date` | Карта: день выписки |
| `grace_debt_amount`, `grace_end_date` | Карта: долг, который нужно погасить, чтобы сохранить льготный период, и день его окончания |
| `min_payment_amount`, `min_payment_due_date`, `min_payment_period_start_date` | Карта: минимальный платёж, его срок и день начала расчётного периода |
| `debt_amount`, `debt_report_date` | Займ: долг по данным банка и день, когда он считан |
| `next_payment_date`, `next_principal_amount`, `next_interest_amount` | Займ: банковская разбивка следующего платежа |

### `categories`

`name`, `color`, `icon`, `parent_id`, `is_excluded_from_stats`, `is_in_recent`, `is_in_quick_selector`, `sort_order`. Категория не может быть своим родителем.

### `display_overrides`

Id `<userId>:<kind>:<targetId>`. Как выглядят встроенные вещи после правки пользователем: `kind` (`category` для `loan_interest` / `loan_fine`, `transaction_type` для `transfer` / `adjustment`), `target_id`, `name`, `color`, `icon`, `parent_id` (только для категорий).

### `loans`

`id` = id кошелька. `principal_amount`, `annual_rate_percent` (null, если договор её не указывает), `start_date`, `first_payment_date`, `closed_date`, `term_months`, `payment_day_of_month`, `schedule_type` (`annuity`, `differentiated`), `prepayment_mode` (`reduce_payment`, `reduce_term`), `interest_accrual` (`monthly`, `daily`), `late_after_days`, `prepayment_window_days`, `payment_wallet_id`, `contract_number`, `description`. См. [Кредиты и займы](/ru/reference/credit-and-loans).

### `loan_schedule_overrides`

Id `<loanId>:<paymentNumber>`. Только строки, отличающиеся от сгенерированного графика: `loan_id`, `payment_number`, `due_date`, `principal_amount`, `interest_amount`, `total_amount`, `source` (`bank`, `manual`).

### `currencies`

Id `<userId>:<code>`. Собственные валюты пользователя и правки встроенных; встроенная валюта без строки используется как есть. `code`, `name`, `symbol` (null = встроенный), `minor_display` (`auto`: дробная часть только если она не ноль, `always`, `never`), `scale` (только для своих валют, 0..9), `manual_rate` + `manual_rate_currency_code` (единица стоит `manual_rate` той валюты; задаются вместе, null = рыночный курс).

### `user_settings`

`id = user_id`. `base_currency_code`, `locale`, `timezone`, `is_payment_reminders_enabled`.

### `forecast_settings`

`id = user_id`. `horizon_months`, `history_months`, `regular_min_months`, `regular_amount_mode` (`median`, `average`, `max`, `last`), `card_payment_mode` (`minimum`, `full_debt`), `is_by_parent_category`.

### `forecast_categories`

Id `<userId>:<categoryId>` (id пользователя входит в ключ, потому что `loan_interest` и `loan_fine` одинаковы у всех). `category_id`, `is_included`, `monthly_amount` со своим `currency_code` (задаются вместе).

### `stat_views`

`scope`, `name`, `config` (JSON), `is_active`, `is_auto_rule_enabled`, `auto_rule` (JSON), `sort_order`.

### `exchange_rates`

Глобальная, id `<YYYY-MM-DD>:<source>`, без `user_id` и `created_at`. `date` (календарный день), `rates` (JSON-карта курсов к USD), `source`, `updated_at`. Повторная загрузка одного дня - один upsert.

### Серверные таблицы

Не синхронизируются на клиенты:

- `push_subscriptions`: `endpoint`, `p256dh_key`, `auth_secret`, `user_agent`; id создаёт сервер.
- `payment_reminder_deliveries`: один пуш на `user_id`, `wallet_id`, `kind`, `due_date`, с `sent_at`; клиенты могут читать свои строки.
