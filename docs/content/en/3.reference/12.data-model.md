## Overview

The server schema lives in `app/supabase/migrations/20261019120000_data_model.sql`. The client mirrors it through one column map, `app/services/powersync/columns.ts`. The rules below explain why the tables look the way they do; every new table or column follows them.

## Storage

1. **Entity** (its own life, many per user, referenced by others): its own table (`wallets`, `categories`, `transactions`).
2. **One record per (user, thing)**: its own table with a **deterministic id**, so a concurrent create on two offline devices lands on one row. The id is the thing's key parts joined with `:`, with no table prefix:
   - one part is the id itself: `loans.id` and `bank_reports.id` are the wallet id;
   - several parts are joined: `loan_schedule_overrides.id` is `<loanId>:<paymentNumber>`;
   - when a part can be the same for two users (a built-in category, a transaction type, a currency code), the user id is a part too: `<userId>:<kind>:<targetId>`. A check constraint pins the format, so no user can take another user's id.
3. **Details of one kind of entity** (a loan, the bank's figures): a 1:1 table whose `id` is the entity's id, with no separate `wallet_id` column. A single field stays a nullable column on the generic table (`wallets.credit_limit`) until a second one comes. A server query joining a 1:1 table by id also matches `user_id`, since the id is written by the client and has no foreign key.
4. **User scalar setting**: a typed column in `user_settings`. A feature with its own group of settings gets a 1:1 table with `id = user_id` (`forecast_settings`).
5. **Device-only UI state**: `useStorage`, never the server. It is never migrated; when the ids it holds change, it starts over from defaults.
6. **JSON column** only for an opaque config that one screen reads and writes whole (`stat_views.config`, `stat_views.auto_rule`, `exchange_rates.rates`). It needs a `version` key, zod defaults and a `jsonb_typeof = 'object'` check, and its column kind is `json` in the column map. JSON is one column for conflict resolution: two offline edits of different keys overwrite each other.

## Every synced table

- **`id`**: generated on the client as a UUIDv7 by `generateId` (`app/utils/generateId.ts`), time-ordered so index inserts stay local. A reference to it is `uuid` too. A deterministic composite id (`<loanId>:<paymentNumber>`) and a column that may hold a reserved id (`category_id`, `display_overrides.target_id`) are `text`; a deterministic id that is one other id (`loans.id`, `bank_reports.id`) is `uuid`. On the client every id is opaque text.
- **Owner and time**: `user_id uuid not null`, `created_at` and `updated_at` (`bigint` ms, `not null`, with a server default for SQL and service-role writers). `updated_at` is metadata every writer sets.
- **Access**: owner RLS through one function, `private.can_access(user_id)`. It is `language sql stable` and not security definer, so the planner inlines it to `user_id = (select auth.uid())` at no per-row cost. Every policy of every table calls it, so sharing data later changes one function. Each table has `enable row level security`, no grants for `anon`, and `select, insert, update, delete` for `authenticated`.
- **Indexes**: a server index for RLS and edge-function queries, usually on `user_id`; a composite index that starts with `user_id` replaces the plain one (`transactions (user_id, date)`, `loan_schedule_overrides (user_id, loan_id)`). The client SQLite schema has no indexes: the stores read whole tables.
- **Sync**: the table is in the `powersync` publication **and** has a line in `app/powersync/config/sync-config.yaml`. A sync-rule line alone syncs nothing.
- `exchange_rates` is the one global table: no `user_id`, read-only for clients, written by the `fetch-rates` edge function.

## Conflicts

The upload of an edit is a PATCH with only the changed columns, and the server applies it as is: **the last upload wins per column**. There is no stale-write guard: with one owner and a few devices the loss is rare (an offline edit of the same column arriving after a newer one), while a row-level guard would also drop offline edits of other columns, silently.

Deletes are hard deletes. A deterministic id re-created offline resurrects a row deleted on another device; that is accepted.

## No foreign keys

Synced tables have no foreign keys. A device deletes a wallet while an offline one adds a transaction to it; on upload the constraint would reject the transaction, the fatal error drops it from the queue, and it is lost. Instead:

- readers skip rows whose target is gone, and delete flows remove dependants (deleting a wallet deletes its transactions, its loan and its `bank_reports` row);
- check constraints inside a row stay;
- a synced table has no unique constraint across rows (it would reject an offline create the same way); uniqueness comes from deterministic ids;
- server-only tables may use foreign keys and unique constraints.

A check constraint that the client does not validate the same way drops the row on upload, so every constraint has a matching client validation (the zod schemas, such as `trnItemSchema` in `app/app/components/trns/types.ts`) tested on the same cases. Rules that span rows (a same-currency transfer with two different amounts, a wallet currency changed while it has rows) are client rules only.

## Enum-like values

Enum-like columns are `text` with a check constraint (a Postgres enum cannot drop a value). Values are snake_case: `credit_card`, `reduce_payment`, `full_debt`. Ranges and signs are checked too.

## Money

- Money is `bigint` in the currency's **minor units** (kopecks, cents, satoshi): exact in Postgres, SQLite and JS (safe up to 2^53). A money column is `amount` or ends in `_amount`; `credit_limit` is money too.
- The scale of each currency is pinned forever in `app/utils/money/scale.ts`: the ISO 4217 minor unit for fiat; crypto at its native decimals capped at 9 (`BTC` 8, `USDT` 6, `ETH` and `SOL` 9). It is never read from `Intl` at run time, because a stored amount must not change meaning when a browser's currency data does. A currency missing from the table (and not among the user's custom currencies) is refused. A user's custom currency carries its own `scale` in `currencies`.
- `toMinor`, `fromMinor` and `formatMinor` live in the same module; edge functions and external writers use the same scales. Display divides by the scale, input parses into minor units.
- A conversion between currencies stays unrounded through a sum and is **rounded once, at the end** (`getTotal` returns base-currency minor units, each rounded once).
- The currency of an amount is the row's `currency_code`, or, when the row has none, the currency of the wallet it belongs to (`transactions`, `bank_reports`, `loans`, `loan_schedule_overrides`). Changing a wallet's currency while it holds amounts would change their meaning, so it is a client rule. A base-currency amount stores its own `currency_code` (`forecast_categories.monthly_amount`).
- Rates and percentages are `double precision`, and the name says the unit (`annual_rate_percent`).

## Days and instants

- **Civil day**: `bigint` UTC-midnight ms, the name ends in `_date` (`date` alone is allowed for the row's own day), with a check constraint `% 86400000 = 0`. An instant written into a day column is rejected instead of landing on a day that depends on the reader's timezone.
- **Instant**: `bigint` ms, the name ends in `_at`.

## Booleans and codes

Booleans are named `is_` / `has_`: Postgres `boolean`, SQLite 0/1. A nullable boolean means "inherit", and its column comment names the source (`wallets.is_in_forecast`: null follows `is_withdrawable`). Currencies are `currency_code` (ISO 4217 or a custom code).

## Naming

- Tables and columns are snake_case; TypeScript is camelCase. The mapping is mechanical (`from_wallet_id` <-> `fromWalletId`) and done by the column map.
- Tables are plural nouns without abbreviations; a feature's tables share its prefix (`loans`, `loan_schedule_overrides`).
- References are `<entity>_id`. No reserved SQL keywords as names (`order`, `desc`, `user`); non-reserved ones like `date`, `type`, `name` are fine.
- A name says what the value is, not where it came from. When the source matters it is a table (`bank_reports`), not a column prefix.
- Column names also live in strings typecheck does not see: raw SQL in `app/services/powersync/mutations.ts` and the stores' `watchTable` queries, the sync rules, and PostgREST filters in edge functions. A rename searches them all.

## The column map

`TABLE_COLUMNS` in `app/services/powersync/columns.ts` lists every synced column with its kind: `bool`, `day`, `instant`, `int`, `json`, `money`, `real`, `text`, `uuid`. From it the client builds:

- `AppSchema` (`AppSchema.ts`): the SQLite tables; `real` is a real column, `text`, `uuid` and `json` are text, everything else is an integer;
- `rowToItem` / `itemToRow`: snake_case <-> camelCase, 0/1 <-> boolean, JSON text <-> object, numbers rounded to integers on write; null columns are left out on read so zod defaults apply;
- `JSON_COLUMNS`: the columns the upload connector sends as JSON objects. Without it a JSON column would upload as a string, fail the `jsonb_typeof` check, and the op would be dropped as fatal.

A compile-time check at the bottom of the file keeps the map equal to the generated Postgres types, so a column added to the database and not to the map fails typecheck.

## Process

- **One migration per feature.** With it come the sync rule, the column map entry, transforms with tests, the demo-mode path, and edge functions when they touch the table.
- **Generated types**: `pnpm db:types` (in `app/`) writes `app/services/supabase/database.types.ts` from the local database. The file is checked in; the column map check and edge functions use it.
- **Schema-version wipe**: a change of the data schema bumps `DATA_SCHEMA` in `app/services/powersync/db.ts`. On boot `ensureDataSchema()` (`app/app/composables/useDataSchema.ts`) compares it with the value stored on the device; when it differs, it drops the local SQLite (synced again from the server), the cold-start store cache, and demo data (a demo user starts over from the login screen). Upload ops still queued under the old schema are lost.
- **External writers**: the app works fully without any external writer. Every value one may provide (`bank_reports`, `loan_schedule_overrides` with `source = 'bank'`) is optional and can be entered by hand, and each feature reading it falls back to the app's own calculation. An external writer through the API follows the same rules: RLS or the service role, constraints, `updated_at`.

## Schema

All synced tables also have `id`, `user_id`, `created_at`, `updated_at` unless noted.

### `transactions`

`type` (`expense`, `income`, `transfer`, `adjustment`), `date` (civil day), `from_wallet_id` / `from_amount`, `to_wallet_id` / `to_amount`, `category_id`, `description`. `created_at` is the moment the row was entered and is kept across edits. See [Transaction Types](/en/reference/transaction-types) for the flow model.

### `wallets`

`name`, `color`, `currency_code`, `type` (`cash`, `bank_account`, `credit_card`, `loan`, `deposit`, `crypto`, `debt`), `sort_order` (the one wallet order on every device), `description`, `is_archived`, `is_excluded_from_total`, `is_withdrawable`, `is_in_forecast` (nullable: null follows `is_withdrawable`), `credit_limit` (money, null unless `credit_card`).

### `bank_reports`

`id` = the wallet id, any wallet type. The latest figures the bank shows for the wallet, entered by hand or written through the API; every column is nullable:

| Column | Meaning |
|--------|---------|
| `balance_amount`, `balance_date` | The balance the bank shows and the day it is for (set together) |
| `statement_date` | Card: the statement day |
| `grace_debt_amount`, `grace_end_date` | Card: debt to repay to keep the interest-free period, and the day it ends |
| `min_payment_amount`, `min_payment_due_date`, `min_payment_period_start_date` | Card: the minimum payment, its due day, and the day its billing period started |
| `debt_amount`, `debt_report_date` | Loan: the debt the bank reports and the day it was read |
| `next_payment_date`, `next_principal_amount`, `next_interest_amount` | Loan: the bank's split of the next payment |

### `categories`

`name`, `color`, `icon`, `parent_id`, `is_excluded_from_stats`, `is_in_recent`, `is_in_quick_selector`, `sort_order`. A category cannot be its own parent.

### `display_overrides`

Id `<userId>:<kind>:<targetId>`. How the built-in things look, edited by the user: `kind` (`category` for `loan_interest` / `loan_fine`, `transaction_type` for `transfer` / `adjustment`), `target_id`, `name`, `color`, `icon`, `parent_id` (categories only).

### `loans`

`id` = the wallet id. `principal_amount`, `annual_rate_percent` (null when the contract states none), `start_date`, `first_payment_date`, `closed_date`, `term_months`, `payment_day_of_month`, `schedule_type` (`annuity`, `differentiated`), `prepayment_mode` (`reduce_payment`, `reduce_term`), `interest_accrual` (`monthly`, `daily`), `late_after_days`, `prepayment_window_days`, `payment_wallet_id`, `contract_number`, `description`. See [Credit and Loans](/en/reference/credit-and-loans).

### `loan_schedule_overrides`

Id `<loanId>:<paymentNumber>`. Only rows that differ from the generated schedule: `loan_id`, `payment_number`, `due_date`, `principal_amount`, `interest_amount`, `total_amount`, `source` (`bank`, `manual`).

### `currencies`

Id `<userId>:<code>`. The user's own currencies and edits of built-in ones; a built-in currency without a row is used as the built-in list has it. `code`, `name`, `symbol` (null = the built-in's), `minor_display` (`auto`: the fraction only when it is not zero, `always`, `never`), `scale` (custom currencies only, 0..9), `manual_rate` + `manual_rate_currency_code` (one unit costs `manual_rate` of that currency; set together, null = the market rate).

### `user_settings`

`id = user_id`. `base_currency_code`, `locale`, `timezone`, `is_payment_reminders_enabled`.

### `forecast_settings`

`id = user_id`. `horizon_months`, `history_months`, `regular_min_months`, `regular_amount_mode` (`median`, `average`, `max`, `last`), `card_payment_mode` (`minimum`, `full_debt`), `is_by_parent_category`.

### `forecast_categories`

Id `<userId>:<categoryId>` (the user id is a part because `loan_interest` and `loan_fine` are the same id for every user). `category_id`, `is_included`, `monthly_amount` with its `currency_code` (set together).

### `stat_views`

`scope`, `name`, `config` (JSON), `is_active`, `is_auto_rule_enabled`, `auto_rule` (JSON), `sort_order`.

### `exchange_rates`

Global, id `<YYYY-MM-DD>:<source>`, no `user_id` or `created_at`. `date` (civil day), `rates` (JSON map of USD-based rates), `source`, `updated_at`. A repeated fetch of one day is one upsert.

### Server-only tables

Not synced to clients:

- `push_subscriptions`: `endpoint`, `p256dh_key`, `auth_secret`, `user_agent`; the server makes the id.
- `payment_reminder_deliveries`: one push per `user_id`, `wallet_id`, `kind`, `due_date`, with `sent_at`; clients may read their own rows.
