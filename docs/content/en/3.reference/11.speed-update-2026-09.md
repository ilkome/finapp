Two changes shipped in `8.3.0-beta.213` (2026-09-26):

1. **Hidden pages stop recomputing.** Pages cached by keep-alive are paused while hidden.
2. **Local database on OPFS.** On Chromium browsers the local SQLite moved from IndexedDB to OPFS with a parallel read connection.

## Results

Phone: Samsung S21 Ultra, Chrome 153 PWA, prod build. Medians, measured back to back in the same session on beta.212 and beta.213.

Data on the measured account (a real one, the same on phone and desktop):

| Data | Amount |
|---|---|
| Transactions | 7 800 (May 2014 - Sep 2026) |
| Wallets | 29 |
| Categories | 166 |
| Loans / schedule rows | 4 / 147 |
| Saved stat views | 4 |
| Currency rate rows (shared) | 59 |
| Local database on the phone | 11.6 MB (+1 MB WAL) |

### Editing a transaction

Time from `saveTrn` until Vue has finished re-rendering (main-thread cost of one edit).

| Scenario | Before | After |
|---|---|---|
| A. Fresh start, dashboard only | 99 ms | 88-90 ms |
| B. After visiting wallets, wallet pages, categories, category pages, history | 196-210 ms | 86-92 ms |

Before, every visited page kept recomputing its statistics on each edit, so an edit got slower the more pages you had opened. Now B equals A: the cost no longer grows with visited pages. Returning to a hidden page after an edit takes 116 ms on the phone (104 ms without an edit in between): the deferred update runs once, on return.

### Cold start

Time from app start until each table's first data arrives from the local database. The first paint comes from the snapshot cache and did not change (~0.9 s); what got faster is the moment live data replaces the cache.

| Table | Before | After | Change |
|---|---|---|---|
| `user_settings` | 764 ms | 535-628 ms | -20 % |
| `wallets` | 1 078 ms | 682-785 ms | -32 % |
| `trns` | 1 834 ms | 1 040-1 104 ms | -42 % |
| `stat_views` | 1 813 ms | 815-859 ms | -54 % |

Desktop with the same data (headless Chromium, CPU throttled 4x/6x, local backend) gains less, -6..-19 % on `trns`: IndexedDB is relatively faster there, and the gain grows the slower the CPU.

## What changed

### Pausing hidden keep-alive pages

`app/app/layouts/default.vue` keeps Dashboard, Wallets, WalletsId, Categories and CategoriesId alive so switching between them is instant. A kept-alive page stays subscribed to the stores, though, so every store change re-rendered it and re-ran its stat pipeline while nobody saw it.

`usePauseWhenInactive()` (`app/app/composables/usePauseWhenInactive.ts`), called in each kept-alive page, pauses the effect scopes of the page's whole component subtree on deactivate and resumes them on activate. Component scopes in Vue are detached from their parent's, so pausing only the page root would leave its children running. Effects that became dirty while paused run once on resume.

Keep-alive itself stays: navigation is still instant, and pages still keep their state and scroll position.

### OPFS with parallel reads

- **Before (beta.212):** the local SQLite lived in IndexedDB (`IDBBatchAtomicVFS`) in every browser. It has a single connection, so all eight boot queries (`user_settings`, `rates`, `categories`, `wallets`, `loans`, `loan_schedule_rows`, `trns`, `stat_views`) queued behind each other, and every page read went through IndexedDB transactions.
- **After (beta.213):** `app/services/powersync/db.ts` opens the local database with `OPFSWriteAheadVFS` plus one additional read connection. OPFS is a real file for SQLite, and in WAL mode reads run in parallel instead of queueing, and file I/O is faster.
- **Where:** Chromium 121+ (Chrome on Android, Chrome/Edge/Brave on desktop). The VFS needs `createSyncAccessHandle({ mode: 'readwrite-unsafe' })`, which only Chromium has. iOS (all browsers are WebKit) and Firefox stay on IndexedDB, unchanged.
- **Precache:** the service worker now caches both wa-sqlite builds: the sync one for OPFS and the async one for the IndexedDB fallback (+1.1 MB).

## Trade-offs

- **Two storage paths.** Chromium runs on OPFS, iOS and Firefox on IndexedDB. Both are covered by the offline e2e (`offline` and `offline-idb` projects) and by unit tests for choosing the path.
- **A database worker per tab.** OPFS sync access handles exist only in dedicated workers, so tabs cannot share one database worker. On Android nothing changes: PowerSync already disables multi-tab mode there. On desktop each open tab holds its own WASM, SQLite cache and reader worker - more memory with many tabs. Sync still runs in one shared worker, and tabs see each other's writes in ~0.3 s.
- **VFS maturity.** `OPFSWriteAheadVFS` is the newest wa-sqlite VFS; keep `@powersync/web` pinned and re-run the offline e2e on upgrades.

## How it was measured

Tools: `pnpm --filter @finapp/app perf:edit --runs 10 --trn <id>` (scenario B adds `--visit`) and `pnpm --filter @finapp/app perf:boot --runs 3` over Chrome DevTools Protocol. On the phone via `adb forward tcp:9222 localabstract:chrome_devtools_remote`, with the app on screen; on desktop against headless Chromium on a prod build with `Emulation.setCPUThrottlingRate`.

Each `perf:edit` run makes 2 warm-up edits (not counted), then 10 timed edits of the same transaction, alternating the amount and putting it back. Each `perf:boot` run reloads the app N times and takes the median. Before every edit round the app was restarted, so hidden pages from earlier visits did not skew scenario A.

### Phone (7 800 transactions)

| Measurement | Before (beta.212) | After (beta.213) |
|---|---|---|
| Edit, scenario A | 2 rounds × 10 edits | 2 rounds × 10 edits |
| Edit, scenario B | 2 rounds × 10 edits | 2 rounds × 10 edits |
| Cold start | 2 rounds × 3 reloads (morning and right before the update) | 2 rounds × 3 reloads, after the first sync into OPFS |
| Return to a hidden page | - | 3 rounds × 4 pages, with and without an edit (24 navigations) |

One more "before" edit round on an app that had been open for hours was discarded: pages kept alive from earlier visits made scenario A read like B (206 ms).

### Desktop

| Measurement | Runs |
|---|---|
| Keep-alive, demo ~1 200 transactions, 4x CPU | 3 prod builds (before, keep-alive off, after) × A and B × 10 edits = 60 edits |
| Return to a hidden page, demo, 4x CPU | before and after × 6 rounds × 4 pages, with and without an edit = 96 navigations |
| Page text after returning, demo seed 42 | 4 pages, before and after builds, text compared character by character |
| Cold start, dev data copy (7 800 transactions) | IndexedDB and OPFS builds alternated: 2 rounds at 4x with an earlier build, then 2 rounds at 4x and 2 at 6x; 5 reloads each = 60 reloads |

### Correctness

- Unit: the whole suite, including the new pause test (it fails without the fix) and 3 tests for choosing the storage (Chromium 121+ with OPFS, other browsers, the version and OPFS checks).
- Offline e2e (8 scenarios: first sync, queued offline write, refused sign-out, offline reload, queue drain, revoked session, other user wipe, sign-out) in two projects: `offline` on OPFS and `offline-idb` on IndexedDB (the path of iOS and Firefox), 16/16. The first scenario asserts which storage each project actually used.
- Browser scenarios on the dev data copy: the first sync into OPFS brings in all 7 800 transactions; cross-tab visibility for both storages and both directions (4 runs, ~0.3 s each).
- Phone: after the update the app runs on OPFS with all 7 800 transactions.
