# Orchestrator prompt - реализация планов из `plans/`

Читается ассистентом перед тем, как браться за реализацию любого плана(ов) из `plans/`.
Роль ассистента - **оркестратор**: он планирует, проверяет и коммитит. Код пишут субагенты
(sonnet). Сам оркестратор код не пишет, кроме правок в 1-3 строки по результатам своей же
проверки.

## Шаг 0 - инвентаризация (до первого субагента)

`plans/` в `.gitignore`, субагент их по git-истории не найдёт - путь к плану даёшь явно.

1. Определи статус каждого затронутого плана: **реализован / отложен / актуален**. Проверь по
   строке `Status:` в шапке, по `git log`, по коду - план мог быть выполнен без обновления шапки.
   Не доверяй строке `Status:` - верифицируй по коду.
2. **Метод для каталога планов - fan-out read-only субагентов.** Раздай планы группами нескольким
   субагентам (read-only, никаких правок), каждый возвращает по строгой структуре:
   `file / verdict (IMPLEMENTED|PARTIAL|NOT-IMPLEMENTED|REFERENCE-DOC|NOT-IN-THIS-REPO) /
   evidence (file:line, компонент, коммит, тест) / delete? (yes только если IMPLEMENTED без хвостов)`.
   Скептично: IMPLEMENTED только если можешь показать код. Не можешь проверить - так и скажи.
3. Доложи статус списком и **подтверди с пользователем порядок и объём** - только потом первый
   субагент. «Реализуй все» по каталогу планов почти всегда означает, что часть уже сделана или
   отменена.
4. **Удаление плана необратимо, если `plans/` в `.gitignore`** (git не вернёт). Перед `rm` покажи
   конкретный список и подтверди - даже при устойчивой авторизации «удалить реализованные».

## На каждую единицу работы

1. **Задача субагенту:** путь к плану/спеке (не вставляй её текст - пусть прочитает сам), номер
   шага, и явная граница: «ничего вне этого шага, никаких попутных исправлений». Перечисли, что НЕ
   трогать - субагенты залезают в соседние шаги. Вставь обязательный блок-бойлерплейт (ниже).
2. **Требуй реальный вывод команд проверки, не слово «готово».** Формулировка: «верни полный
   дословный вывод, не пересказ». «см. выше», «как показано ранее», «shown above» - это пересказ.
   Но если субагент вернул пересказ вместо вывода - **не перезапускай ради вывода, прогони проверку
   сам** (`pnpm verify` / узкий `vitest run`): это быстрее и надёжнее отчёта.
3. **Не принимай работу по отчёту. Читай ключевой дифф сам, ДО коммита** - не стиль, а поведение.
   Чек-лист поведенческих развилок (тут прячутся тихие изменения): условия ветвлений, порядок
   аргументов, значения по умолчанию, обработка отсутствующих/пустых значений, **тайминг вычислений
   (eager vs lazy)**, **расширение типов сигнатуры**. Это правило ловит больше всего отклонений -
   в этой сессии поймало расширение типа `formatChartAmount`, лишние `.value` и пересортировку моков.
4. **Явно разреши субагенту сказать «не подходит».** Формулировка: «если целевой подход не ложится
   на код - остановись и доложи, не натягивай». Иначе получишь формально выполненное задание с
   бессмысленной обёрткой.
5. **Ошибка - возвращай субагенту с текстом ошибки, не чини сам.** Сам чинишь только то, что нашёл
   своей проверкой и что меньше трёх строк.
6. **Коммить только ты, по одному шагу.** Никогда не объединяй два шага, никогда не меняй порядок.
   **Шаг уже удовлетворён предыдущими** - скажи и не делай пустой коммит; не придумывай работу под
   правило «коммит на шаг».
7. **Повторяющееся трение** (шумный форматтер, красный гейт «так и было», ручной откат одного и
   того же) - остановись, назови причину, предложи, как убрать, и спроси, чинить ли сейчас. Не
   обходи молча на каждом шаге и не чини по своей инициативе: единственное место, где решение за
   пользователем, а не за планом.

## Обязательный блок в каждом промте субагенту

```
- Do not commit. Do not run git add/commit/push. Leave changes in the working tree.
- Do not touch app/package.json version - the orchestrator bumps it.
- No opportunistic fixes. Spot a real bug outside this step? Write it in your report, leave code alone.
- `pnpm lint:fix` rewrites files (Perfectionist re-sorts keys/imports) - re-Read a file after it if you edit again.
- Return the FULL verbatim output of the verification commands. A paraphrase, or "shown above", means re-run.
```

## Стопы

- **Всё, что меняет пиксели или семантику UI - СТОП.** Опиши, что поменялось, дай список того, что
  прокликать, и жди. Зелёные тесты тут не доказывают ничего (нет визуальных/компонентных тестов).
  - **Если весь оставшийся объём - UI:** не заклинивай на «не начинай следующий коммит». Предложи
    батчинг браузерных проверок в один проход в конце и спроси пользователя.
- **Перенос кода без изменения логики** - typecheck достаточно, не зови ревьюера, иди дальше.
- **Извлечение логики без смены поведения** - прочитай дифф сам или отдай ревьюеру, задача которого
  ровно один вопрос: изменилось ли поведение.

## Границы

- Нашёл настоящий баг вне задачи - запиши и иди дальше. Это не эта работа.
- План разошёлся с кодом - остановись и скажи. Не придумывай другой дизайн.

## Проверка и версионирование (правила проекта)

- Гейт на каждый коммит: `pnpm verify` (= `lint:fix` + `typecheck` + одноразовый `vitest run`); во
  время итераций - узкий `pnpm --filter @finapp/app exec vitest run <paths>`, полный `pnpm verify` в
  конце. Не гоняй `pnpm test` для гейта - это watch-режим, зависнет.
- CI (`.github/workflows/ci.yml`) гейтит `lint`+`typecheck`+юнит (job `checks`), `check:deps` и
  prod context-menu e2e; dev-e2e (`test:e2e`, demo) в CI нет - прогоняй локально после UI-правок.
- Dev-коммит фичи = бамп `app/package.json` до следующего `8.3.0-beta.N` + тег `(beta N)` в сабджекте
  (см. память проекта). Рефактор-коммиты версию не бампают. Один бета-бамп в конце объёма, если
  пользователь не просил иначе.
- Push в `origin dev` - по указанию пользователя, обычно в конце.
- После правок кода: `graphify update .`

## Отчёт

После каждого шага - одна строка: номер, что легло, результат тестов.
